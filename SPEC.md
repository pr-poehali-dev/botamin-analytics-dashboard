# ТЗ: Модуль «Касания + Аналитика» для CRM

> Готовый промпт-задание для нового проекта на платформе.
> Вставляй целиком или по разделам. Модуль встраивается в **существующую CRM**,
> где уже есть список контактов. Мы добавляем к контактам вкладку **«Касания»**
> (звонки + сообщения из мессенджеров в единой ленте) и вкладку **«Аналитика»**
> (ИИ-сводка состояния клиента и рекомендация к следующему касанию).

---

## 1. Суть продукта (в двух словах)

Коммуникационный центр внутри CRM. По каждому клиенту (ключ — **номер телефона**)
собирается единая история касаний из всех каналов: звонки и переписки в
мессенджерах. Звонки автоматически транскрибируются, вся история клиента
анализируется ИИ. Результат — **короткая сводка состояния клиента** и
**рекомендация к следующему касанию**. Из системы можно **и написать, и позвонить**.

**Важно, чего НЕ делаем** (упрощаем относительно старого проекта):
- Нет ручной загрузки Excel-файла и мастера «загрузка → парсинг → транскрибация».
- Нет перегруженного дашборда с десятком фильтров и графиков.
- Данные приходят **автоматически по вебхуку**, обрабатываются в фоне.

## 2. Каналы касаний (источники)

Единая абстракция **«канал»** (channel provider). Реализуем сразу:

| Канал | Направление | Статус |
|---|---|---|
| **Входящие звонки** (вебхук от АТС) | приём + транскрибация | ядро, сразу |
| **Telegram** | приём + отправка | сразу (бесплатно, свой бот) |
| **MAX (max.ru)** | приём + отправка | сразу |
| **Avito** | приём + отправка | сразу |
| WhatsApp, VK, исходящие звонки, Email | — | позже, тем же адаптером |

### Архитектура каналов — единый адаптер
Каждый канал реализует один и тот же интерфейс провайдера:

```
ChannelProvider:
  - name: str                       # "telegram" | "max" | "avito" | "call" ...
  - send_message(to, text, attachments) -> message_id
  - parse_webhook(event) -> IncomingTouch   # нормализует входящее в единый формат
  - verify(event) -> bool                    # проверка подписи/токена вебхука
```

Каждый мессенджер подключается через свой вебхук. Провайдер приводит любое
входящее событие к единой структуре `Touch` (см. модель данных). Смена сервиса
(например переход на агрегатор UIS Omni / Wappi.pro) = добавление нового
провайдера, без изменения остального кода.

> **Про бюджет и легальность (зафиксировать для владельца):**
> - Telegram — бесплатно (Bot API).
> - MAX / Avito — по их официальным API (у Avito Messenger API — по заявке).
> - WhatsApp — только официальный Cloud API или платный шлюз; серые библиотеки = риск бана.
> - Телефония (исходящие звонки, номер, минуты) — всегда платная.

## 3. Экраны (UI)

Минимальный, чистый набор. Встраивается в существующую CRM.

### 3.1. Вкладка «Касания» (в карточке контакта)
Единая **лента диалога** по клиенту, все каналы вперемешку по времени:
- Пузыри сообщений: слева — входящие (клиент), справа — исходящие (мы).
- Иконка канала на каждом касании (звонок / TG / MAX / Avito).
- Звонок в ленте = карточка: длительность, кнопка «▶ Слушать», свёрнутый
  транскрипт (раскрывается), статус транскрибации/анализа.
- **Поле ввода снизу**: выбор канала → написать → отправить. Плюс кнопка
  «Позвонить» (когда подключена телефония).

### 3.2. Вкладка «Аналитика» (в карточке контакта)
ИИ-сводка по всей истории клиента:
- **Сводка состояния клиента** — 2-4 предложения: где сейчас клиент, чего хочет,
  какие возражения/риски, уровень интереса.
- **Рекомендация к следующему касанию** — конкретное действие: что, когда и по
  какому каналу написать/сказать.
- Ключевые показатели: интерес (высокий/средний/низкий), стадия, целевой/нет,
  последняя активность.
- Кнопка «Пересобрать анализ».

### 3.3. Список клиентов (усиление существующего списка контактов)
К строкам контактов добавляем:
- бейдж состояния (интерес/стадия),
- короткую рекомендацию к следующему шагу,
- индикатор «есть непрочитанные касания».

### 3.4. Общий дашборд (лёгкий)
Только ключевые цифры, без перегруза: всего касаний за период, распределение по
каналам, конверсия/успех, средняя оценка звонков, топ клиентов «требуют внимания»
(на основе рекомендаций ИИ). Отдельные тяжёлые графики — опционально.

## 4. Логика обработки (главный пайплайн)

```
Вебхук канала → нормализация в Touch → привязка к клиенту по номеру телефона →
  сохранение касания в БД →
  (если звонок) фоновая транскрибация →
  пересбор ИИ-анализа по ВСЕЙ истории клиента →
  обновление сводки + рекомендации в карточке клиента
```

Ключевые правила:
- **Клиент = номер телефона** (нормализовать: убрать пробелы/скобки, привести к
  `+7XXXXXXXXXX`). Для каналов без телефона (например Avito) — маппинг внешнего
  id канала → клиент, с возможностью ручного связывания.
- Всё в фоне, UI не блокируется. Касание появляется сразу, транскрипт/анализ —
  по готовности (индикатор статуса).
- Анализ клиента пересобирается при каждом новом касании (или по кнопке).

## 5. Технологии (переносим из текущего проекта)

- **Frontend:** React + TypeScript + Vite + Tailwind + shadcn/ui. Иконки —
  lucide через обёртку `@/components/ui/icon`.
- **Backend:** Python 3.11 Cloud Functions (по функции на задачу).
- **БД:** PostgreSQL (psycopg2, Simple Query). Схема проекта — своя.
- **Транскрибация звонков:** **AssemblyAI** (`language_code: 'ru'`,
  `speaker_labels: true`, `speakers_expected: 2`). Определение оператор/клиент —
  по ключевым маркерам речи + фолбэк по первой длинной реплике; распознавание IVR
  по ключевым словам.
- **ИИ-анализ:** **Mistral AI**, модель `mistral-small-latest`, `temperature 0.1`,
  ответ строго `json_object`.

- `ASSEMBLYAI_API_KEY` — транскрибация звонков.
- `MISTRAL_API_KEY` — ИИ-анализ и рекомендации.
- `DATABASE_URL` — подключение к БД.
- `TELEGRAM_BOT_TOKEN` — Telegram.
- `MAX_API_TOKEN` — MAX (max.ru).
- `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET` — Avito Messenger API.

## 6. Модель данных (новые таблицы)

Универсальная модель касаний, не привязанная к конкретному каналу.

### `clients` (или расширение существующей таблицы контактов)
- `id` PK
- `phone` VARCHAR — нормализованный номер (ключ склейки)
- `name` VARCHAR
- `crm_contact_id` — связь с существующим контактом CRM
- `state_summary` TEXT — ИИ-сводка состояния клиента
- `next_action` TEXT — рекомендация к следующему касанию
- `interest` VARCHAR ('high'|'medium'|'low')
- `stage` VARCHAR — стадия
- `analysis_updated_at` TIMESTAMP
- `created_at` TIMESTAMP

### `touches` — единая лента касаний
- `id` PK
- `client_id` FK → clients
- `channel` VARCHAR ('call'|'telegram'|'max'|'avito'|...)
- `direction` VARCHAR ('in'|'out')
- `external_id` VARCHAR — id сообщения/звонка в канале (для дедупликации)
- `text` TEXT — текст сообщения или транскрипт звонка
- `audio_url` TEXT — для звонков
- `duration_sec` INTEGER — для звонков
- `attachments` JSONB
- `status` VARCHAR ('received'|'transcribing'|'analyzed'|'sent'|'error')
- `created_at` TIMESTAMP — время касания
- UNIQUE(`channel`, `external_id`) — защита от дублей вебхука

### `call_transcripts` — детальный транскрипт звонка (перенос из старого проекта)
- `id` PK, `touch_id` FK, `comm_id` VARCHAR UNIQUE
- `full_text` TEXT
- `replicas` JSONB — массив `{speaker, speaker_label, text, start_time, segment}`
- `replica_count`, `operator_replicas`, `client_replicas` INTEGER
- `has_ivr` BOOLEAN
- `created_at` TIMESTAMP

### `client_analyses` — ИИ-анализ по клиенту (новое, ключевое)
- `id` PK, `client_id` FK
- `state_summary` TEXT — сводка состояния клиента
- `next_action` TEXT — рекомендация к следующему касанию
- `interest`, `stage`, `outcome` VARCHAR + labels
- `risks` JSONB, `key_points` JSONB
- `created_at` TIMESTAMP

## 7. Backend-функции (Cloud Functions)

1. **`webhook-{channel}`** (по функции на канал: `webhook-telegram`, `webhook-max`,
   `webhook-avito`, `webhook-call`) — приём вебхука → нормализация в `Touch` →
   привязка к клиенту → сохранение → запуск транскрибации (для звонков) и
   пересбора анализа.
2. **`send-message`** — единая отправка: `{channel, client_id, text}` → выбирает
   провайдера → шлёт → сохраняет исходящее касание.
3. **`transcribe`** — транскрибация звонка через AssemblyAI (перенос логики).
4. **`analyze-client`** — берёт ВСЮ историю касаний клиента → Mistral → возвращает
   сводку состояния + рекомендацию к следующему касанию (новый промпт, см. ниже).
5. **`get-touches`** — лента касаний клиента для UI.
6. **`get-dashboard`** — агрегаты для лёгкого дашборда.

Каждая функция: обработка `OPTIONS`/CORS, `Access-Control-Allow-Origin: *`,
`tests.json`, вызов `sync_backend` после изменений.

## 8. Промпты ИИ

### 8.1. Анализ отдельного звонка (перенос, транскрипт → JSON)
Provider: Mistral `mistral-small-latest`, temp 0.1, `json_object`.
Системный промпт (базируется на текущем, поля):
`call_type, call_type_label, qualification, qualification_label, client_interest,
client_interest_label, outcome, outcome_label, fail_reason, success_factor,
operator_score (1-10), operator_followed_script, operator_handled_objections,
operator_comment, summary, key_phrases_client[], key_phrases_operator[]`.

### 8.2. Анализ клиента по всей истории касаний (НОВОЕ — ядро задачи)
На вход — вся лента касаний клиента (звонки-транскрипты + сообщения всех каналов,
по порядку времени, с пометкой канал/направление). Промпт (черновик):

```
Ты аналитик отдела продаж. На вход — вся история общения с клиентом
(звонки и переписки из разных каналов) по порядку времени.
Верни ТОЛЬКО валидный JSON без markdown:
{
  "state_summary": "2-4 предложения: где сейчас клиент, чего хочет, возражения/риски, уровень интереса",
  "next_action": "конкретная рекомендация к следующему касанию: что сказать/написать, когда и по какому каналу",
  "interest": "high|medium|low",
  "interest_label": "Высокий|Средний|Низкий",
  "stage": "короткое название стадии сделки",
  "outcome": "success|failure|pending",
  "risks": ["риск1", "риск2"],
  "key_points": ["важный факт о клиенте 1", "..."]
}
Правила: опирайся только на факты из истории, не выдумывай.
Рекомендация должна быть практичной и конкретной.
```
